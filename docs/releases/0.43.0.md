# 0.43.0 — The Macintosh record is the DOS record, repadded

Research, not a feature: nothing in the app looks different. This is the step
the rest of the saved-game work stands on.

The question was whether the Macintosh's 302-byte character record is the
documented DOS 285-byte one with different padding, or a different design
altogether. **It is the same record.** Both ends line up exactly.

- **The head is unshifted.** The sixteen-byte name, the twenty-one
  memorised-spell slots at `0x17`, the class at `0x2f`, the maximum hit points
  at `0x32` — all exactly where the DOS record puts them.
- **The tail is DOS plus twelve**, field for field, becoming plus sixteen before
  the end.
- **The arithmetic closes.** `285 + 16 + 1` byte of padding `= 302`, the same
  way the Amiga port pads Pool of Radiance's 287 to 288.

## Two things worth more than the alignment

**The eight bytes DOS calls "heap" are where the Macintosh put its two
handles.** This project found a next-member handle and the character's own
handle there by following the game's roster walk, with no idea what the DOS
record did with that space. It does nothing with it. That is what a port does:
it spends the dead space on the memory model it actually has.

**The quick flag is inside DOS's combat-status field.** Found here by capture
and diff, it turns out to be byte 3 of a four-byte field whose byte 0 is the
condition this project also found separately. The two bytes between them are
now the first place to look for whatever else that field carries.

## What is deliberately not claimed

The middle of the record, between `0x32` and `0x10e`, does **not** line up, and
is left open rather than guessed at. The offsets found there imply shifts that
do not increase monotonically, which cannot be right — insertions only ever push
fields later.

The DOS table is second-hand, read from a public project, and is treated that
way. Every Macintosh offset was found independently here months earlier by
reading the game's own 68k code. No code, data or file from that project is
used.

## What it changes for the queue

- **F39 (auto-memorise) is not blocked.** The spell array is the 21 bytes at
  `0x17`, already read, and DOS agrees on position and length.
- **F41 (auto-equip) was never blocked on this.** What it needs is a way to pick
  an item out of inventory.
- **F78 (decoding the save) gains a strong prior** — if the record in memory is
  the DOS record repadded, the record in a save file very likely is too.

**Verified:** a new native suite pins the probe's constants to the *structure*
rather than to a list of numbers, so an offset cannot drift without the
alignment being reconsidered. 499 Java tests, six native probe suites, 25 render
checks.
