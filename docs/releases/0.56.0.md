# 0.56.0 — Loading no longer fights the Finder

Debugging 0.47.0's load sequence turned up one real cause and two designs that
had to go.

## Why it stalled

**`Cmd-Q` does not quit.** It asks *"Do you really want to quit?"* in a dialog
whose buttons carry no default outline — Return does nothing there, and
confirming it would mean clicking at a measured coordinate, which is the exact
fragility this whole sequence exists to avoid.

The sequence's own error message said "it may be asking something on screen".
It was right.

**So it no longer quits.** It restarts the emulated machine — something the app
can already do, which asks nothing — and waits for the game to start itself from
the startup disk's Startup Items.

## And it no longer types into the Finder

When the machine came back up at the desktop, the old sequence typed the
application's name to select it and pressed `Cmd-O`. That only works if the
application is in the frontmost window. When it is not, the typing lands on
whatever else begins with those letters: one run renamed *Adventurer's Journal
Part 1* and opened it, another opened *Apple Extras*.

Guessing at somebody's desktop is not worth a saved game. It now stops and says
the game did not start itself, and what to do about it.

## What is still not proven

**The sequence has still not run to a loaded party.** The emulator used for
testing has a disk set whose game does not launch itself, so the new behaviour
correctly reports that and stops — which is the *refusal* working, not the
feature working. Proving the rest needs a startup disk that launches the game.

A failure remains safe: it stops, says why, and leaves the guest alone.

**Verified:** 581 Java tests, six native probe suites, 58 render checks, the APK
check.
