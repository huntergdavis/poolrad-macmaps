# 0.47.0 — Load a saved game, at any time

**PoolRad → Saved games → Load a saved game** closes the game, starts it again,
and opens the save you chose. The guest is covered while it happens, so you do
not watch menus being worked; one line says which part is under way.

The game only offers Load Saved Game before a game begins — once you are
playing, it is greyed out and only Quit stays enabled. So loading at any time
means quitting first, and the confirmation says plainly that anything unsaved in
the game you are playing now will be lost.

## It lists parties, not file names

`F7Healed` and `F7Injured` tell nobody anything. The chooser reads each save and
shows who is in it — "Zarram, Arax the Bold and 4 others · 2 hurt".

## How it knows what the machine is doing

Not by looking at the screen. The party probe already tells the difference
between **the game not running**, **the game running with no party**, and **a
readable party** — which is exactly the three-way answer this needs, read from
the emulated heap.

Every other refusal the probe can give is a complaint about the heap *while a
game is very much running*, and is deliberately read as "unknown" rather than as
"no game".

**This is built around a failure that already happened.** The scripting harness
once could not tell that Load Saved Game was disabled, typed a save name into
the running game instead, and the party was found altering its marching order.
So every step names the state it is waiting for and stops the whole sequence
rather than pressing on:

- a game that will not close stops everything and says it may be asking
  something on screen;
- a party appearing when the load dialog should be up stops **before a single
  character is typed**;
- a game that never comes back, or a save that never opens, says so and loads
  nothing.

## No coordinates anywhere

Every step is a keyboard equivalent taken from the game's own `MENU` resources —
`Cmd-Q` to quit, `Cmd-O` for the Finder's Open, `Cmd-L` to load. Nothing depends
on where a menu is drawn or whether an item looks grey.

**Verified:** 531 Java tests including sixteen new ones over the sequence and
the state reading — both failure paths above among them — with no Android in
either class. Six native probe suites, 25 render checks, and the APK check that
0.46.0 needed.

**Not verified here:** the sequence has not been run against a live game on the
tablet. The parts that can be tested without one are; the rest is the owner's
own check, and a failure leaves the guest untouched and says why.
